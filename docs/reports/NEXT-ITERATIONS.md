# LFZ 后续迭代计划

日期：2026-10-29。负责人：team-lead。状态：规划；不是已实现规范，也不代表正式发布批准。以T14已推送候选2c0e079为起点，保留现72内置和现有行为；新语义须先由language-architect冻结spec。

## 目标与顺序

优先让Agent可靠地处理失败、复用代码、控制运行成本并调用外部工具。T15先推进，后续依次进入，不同时启动多项语言语义改造。不以新增特性抵消性能门槛。

## 效率与发布贯穿每个迭代

R304保持OPEN，现有19项原线和失败证据不改。T13省分配候选已因实测回归拒收，新增8项回归保留；T14无性能测窗，不能沿用T13读数当成T14成绩。下一轮性能工作先做可解释热点分析和成本定位，候选冻结后一次规定窗口比较，完整保留失败与环境不确定项。不重复择窗追绿，不以源码少分配代替实际吞吐收益。

特性迭代可提交功能候选；正式版本须对实际最终字节完成性能与功能验收。任何门槛调整必须单独决策并重建版本化基线，不能追溯修改旧结果。大数据阶段增加独立峰值内存指标，不凭几档总耗时声称复杂度改善。

## 每个迭代的固定流程与责任

1. team-lead明确范围、非目标和验收应用；requirements-analyst新增可验收条目；language-architect冻结契约、错误和复杂度。
2. 对应源码owner实现最小能力并新增有意义测试；涉及文法由core-dev，运行时由runtime-dev，CLI由tooling-dev。先建立真实缺功能/缺陷的失败见证，不制造必过红测。
3. test-engineer公开黑盒；app-dev更新实际应用；docs-writer与ai-dx-engineer同步人/AI指南并实跑。旧测试不删改。
4. verifier独立复验；perf-engineer在无并发编译测试条件下测冻结候选；源码变更后不能复用旧字节的验收结论。
5. release-manager整理产物、明确逐文件提交分组；team-lead统一回写状态/看板并按既有授权推送。保留原用户三块未提交修改、旧标签、旧v2输入与全部失败证据。

发现语义缺口先修契约；功能或性能失败保留证据并修复或拒收，不为赶下一迭代掩盖开放项。完成一个子阶段后自动推进下一个已规划阶段，无需反复请求“继续”；新增不可逆或超出授权的外部动作另按实际授权处理。

## 暂缓

类/继承、match、可选链、静态类型系统、通用生成器/async、远程包管理、完整LSP不进入近三轮。先用现有struct/闭包/管道与最小接口验证价值。

## 下一步的具体三项交付

T15先完成错误恢复接口设计、包含坏JSON记录的端到端验收样例、回调错误后的depth/trace恢复单测方案。T15功能验收后再启动模块实现，避免两种控制/加载语义同时改造。
