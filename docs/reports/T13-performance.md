## 源码诊断与可解释范围

- `benchmarks/lfz/string_ops.lfz` 的主循环是 `parts = push(..., parts)`；`src/builtins.rs::b_push` 经 `array_snapshot` 复制已有元素后追加，每轮数组长度递增，累计为 O(n²) 个 Value 浅复制。它不是字符串 `s = s + c` 拼接基准，不能以字符串原地追加优化解释该组收益。
- `string_map` 用 `range |> map` 构造数组，避开上述重复复制，仍逐元素进入 `call_value`。当前 `call_value` 的 `args.to_vec()` 是一次确定存在的回调实参分配；若 `call_user` 消费精确长度迭代器，可去除这次中间 Vec，同时保留参数值复制、fresh frame/cell、参数可写性和 traceback。
- `join` 无用户回调，原实现为取只读字符串借用而先复制 Value 数组。可由 runtime-dev/架构师确认后改为直接只读借用容器，避免不必要的 O(n) Value 快照。高阶函数含用户回调，不能据此一并取消输入快照，因为回调可改变原数组，且持有 RefCell borrow 跨调用会改变行为或 panic。
- T12 `string_ops`4k 的同期paired变慢28.8%已保留。三档总时、CPU量化和进程启动污染不足以确定其微观原因；不宣称JSON新增直接导致，不宣称所有差异由上述分配造成。

### 判定与归因边界

- 两项FAIL：string_map2k新17.641ms > 原17.522ms、同期旧14.228ms；small4新22.960ms > 原18.746ms、同期旧16.221ms。即使第一项超幅很小也不四舍五入为通过。
- 两项环境不确定：string_ops2k新32.548/旧34.704均超原28.902ms；string_map8k新23.762/旧23.032均超原22.521ms。不能将环境不确定改成PASS，也不能把旧版超线推断成新候选完全没有回归。
- string_map三档新/T12分别1.162/1.065/1.078，当前总时证据没有证明回调消分配带来可见提速。string_ops8k虽然234.390ms在线236.353内，仍比同期T12 206.177ms慢约13.7%、比旧216.530慢约8.2%；这些回归照实披露。small4比同期T12慢约30.4%。
- 源码确实去除了回调实参中间Vec，以及join只读路径的Value快照；这说明分配/复制路径变化，不能替代整段性能实测结论。此窗同时改变这两项，实现差异与OS/启动噪声共同存在，不能从三标签总时反推精确LLVM或单点因果。
- 数字500k旧106.862/T12 90.747/新89.539ms；真实dist路径90.165ms。结构体8k旧95.424/T12 19.180/新19.488ms，相对旧约79.6%降时，仍满足原至少30%目标，但比T12略慢约1.6%；主要字段索引收益来自T12，不冒充T13新增收益。
- noop12.251ms低于原16.307ms，仅限本窗。array1k绝对PASS但比同期旧慢约33.0%，原线合格与paired领先是不同命题。本窗15/19不比T12历史15/19自动代表相同负载状态或同一环境；原报告/失败记录均保留。
