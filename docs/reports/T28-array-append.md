# T28 数组追加与性能验收

`xs = push(item, xs)` 常用于在循环里收集结果。T27 每次都复制已有的元素，追加 N 次一共要复制 N(N−1)/2 个元素引用。T28 在赋值时核对数组身份、可写性和引用计数。如果旧数组只有这次赋值在使用，解释器将原有 Vec 缓冲移入一个新的数组对象，连续追加的元素搬移成本降为摊还线性。有旧数组别名、嵌套引用或 Rust 弱引用时沿用浅复制。查找赋值目标时一次取出槽位和可写性；局部变量、闭包和模块均沿原名字解析规则。[实现细节](T28-runtime-prototype.md)

## 功能验收

- 最终候选通过 722 项 Rust release 测试及 182 项 LFZ 黑盒。新增黑盒保存旧数组作为历史快照，还覆盖了首参数重新绑定数组与局部同名函数。单元测试也检查了新对象身份和底层缓冲复用。[Rust 日志](../../benchmarks/t28/results/rust-release.log) · [公开测试](../../benchmarks/t28/results/blackbox.json)
- 17 套既有回归、37 项 REPL、27 项格式化测试通过。JSON 路由 9 项、REPL 应用 6 项、人类指南 3 项、AI 指南 4 项实际运行符合预期。[回归命令及输出](../../benchmarks/t28/results/regression-commands.json) · [示例记录](../../benchmarks/t28/results/jsonroute.json)
- 独立验证用 10 组程序逐字节对照 T27 与 T28 的退出状态、标准输出和错误输出，覆盖嵌套共享、自身追加、闭包、错误和预算终止。[独立验收](T28-independent-verification.md)

## 与旧候选及 Python 的对照

Windows 上使用同一启动路径交替运行 T27 和 T28，分别对每一项预热一次、正式运行六次。Python 使用课程基准中对应的 string_ops 程序，输入和预期输出与 LFZ 相同。下表是进程耗时中位数，含进程启动、输入、执行及输出。[LFZ 原始记录](../../benchmarks/t28/results/focused.json) · [Python 版本及原始记录](../../benchmarks/t28/results/python.json)

| 字符串条数 | T27（ms） | T28（ms） | Python（ms） |
| ---: | ---: | ---: | ---: |
| 2,000 | 48.11 | 23.84 | 56.11 |
| 4,000 | 124.24 | 26.31 | 58.05 |
| 8,000 | 271.44 | 32.78 | 59.29 |

在 8,000 项纯整数追加中，无外部共享的中位耗时由 301.90 ms 降至 24.16 ms。每次都保留并读取旧数组的程序耗时为 318.67 → 302.48 ms。这种用法仍需复制以保留快照。Python 的数字仅描述本机这三组完整命令。

## 正式性能门槛与后续定位

原 R304 协议只运行一次。152 个预热和 532 个正式样本全部给出正确输出。19 项绝对门槛中 13 项通过，2 项明确失败，4 项环境不确定（同期旧基线也越线）。三档 string_ops 均通过原门槛，2,000 项为 12.24 ms，原上限 28.90 ms。结构体 8,000 项为 26.96 ms，也通过原降时目标。[原始窗口](../../benchmarks/t28/results/gate.json) · [复算](../../benchmarks/t28/results/gate-assessment.json)

| 明确失败项 | 同期旧基线（ms） | T28（ms） | 原上限（ms） |
| --- | ---: | ---: | ---: |
| array_builtins 10000 | 22.09 | 27.80 | 22.77 |
| string_map 2000 | 12.39 | 19.39 | 17.52 |

四个环境不确定项是空程序、10,000 与 100,000 次数值循环及 1,000 项数组操作。R304 对 T28 仍开放。正式样本没有测峰值内存。

另用 70 次进程启动做分段诊断，每个进程内重复同项操作 16 次。完整数组流水线的中位耗时为 T27 109.81 → T28 115.46 ms，六对中三对 T28 更快。map/filter 段为 87.40 → 89.87 ms；sort/reduce 段为 39.88 → 42.74 ms（含一次输入准备）。完整字符串映射为 50.14 → 47.22 ms，六对中五对 T28 更快。空循环与输出对照本身为 14.44 → 15.70 ms。这些结果可以定位后续优化对象，单凭这次对照无法将正式窗口中的超线归因到追加缓冲区的改动。[诊断脚本](../../benchmarks/t28/diagnose.py) · [逐次输出、顺序及耗时](../../benchmarks/t28/results/diagnosis.json)
