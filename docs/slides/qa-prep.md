## 1. 必答难题（★ 高概率 × 高杀伤力，优先打磨）

### Q1 ★★ 「LFZ 为什么比 Python 慢那么多？最大到 30 倍？」　（概率：高｜杀伤力：高）

**答案要点**：
1. **先把事实说准**：不是全部慢 30 倍。**进程启动 LFZ 更快**（11.67 ms vs CPython 3.13 的 42.34 ms，快 3.6×）；纯计算负载大规模下 LFZ 慢 **1.2×–3.9×**（同数量级）；只有 **struct 键操作（28.8×）与字符串 `push` 建数组（31.2×）** 两处出现超线性。
2. **30 倍的真因是 O(N²)，不是"解释器慢"**：`push` 按语义返回新数组、实现为整表拷贝，反复 push 建 N 元数组即 ΣO(k)=O(N²)；struct 字符串键写/读是线性扫描、无哈希索引。**这是两处容器操作的实现复杂度问题，已用探针（push-only ≈ 全耗时）定位。**
3. **普遍落后部分有明确结构原因**：LFZ 是**树遍历求值 + 运行时按名字查链（无 resolver）**；对照的 CPython 3.13 是带**特化自适应解释器（PEP 659）**的成熟字节码 VM。差距符合预期。
4. **诚实边界**：小规模比值 < 1 **全部来自启动优势，不是 LFZ 算得快**——这一点报告里用 total/net 两条线明确区分，不美化。
5. **不是"Python 上加一层"**：解释器用 **Rust** 实现（D-011），不存在 Python 级解释开销叠加。

**兜底话术**：「完整数据、逐轮原始值和方法口径都在 `docs/reports/performance.md` 与 `benchmarks/results/raw.json`，可现场复核。」

### Q2 ★★ 「为什么用 Rust 实现，却坚持只用标准库、不引任何第三方 crate？」　（概率：高｜杀伤力：高）

**答案要点**：
1. **用户拍板的约束**：实现语言与"仅用 std"由用户确认（决策记录 D-011）；目标是把语言实现本身作为**可控、可审计**的交付物——不把核心逻辑外包给现成库。
2. **需要的能力 std 全覆盖**：动态值用 `enum Value`、可变复合类型用 `Rc<RefCell<...>>`、错误用 `Result<T, LfzError>`；词法/语法/求值都是自研，无需外部依赖。
3. **收益**：`cargo build` 可复现、无供应链风险、评审可只读源码验证；构建 **0 warning / 0 error**。
4. **代价与取舍**：std 没有现成 HashMap 保序结构，故 struct 目前是**线性扫描**（正是 Q1 的性能债之一）；优化方案（IndexMap 式：HashMap<key→slot> + 顺序数组）也**可用 std 实现**，无需引库。
5. **诚实**：这不是"不能用库"，而是课程交付场景下有意的工程选择。

**兜底话术**：「所有依赖决策都在 `DECISIONS.md` 与 `PROJECT_STATE.md`，可查。」

### Q3 ★★ 「`#42` 这种奇怪的规定有什么意义？纯属搞笑吗？」　（概率：高｜杀伤力：中）

**答案要点**：
1. **设计动机有三层**：① **辨识度**——LFZ 独一无二的语言签名，与任何现存语言都不同（课程明确要求"不能与现存语言完全相同"）；② **仪式感**——「宇宙的答案」是开发者友好、易记的记忆点；③ **强制文件校验**——缺失即 `CosmosAnswerError`，把"文件入口合法性"做成一等检查。
2. **它不是注释**：`#` 只在前导位合法，程序中间出现 `#` 是 `SyntaxError`；规则**极其严格、无变体**（`# 42`、`#42␣`、`##42`、首行前空行全部非法），仅按 **`.lfz` 扩展名**触发。
3. **有完整规范**：`docs/spec/syntax.md` §2.2 给了逐字节的加载器算法、按扩展名判定、BOM/行终止符可移植性策略，以及 A1–A27 的歧义审计。
4. **工程验证**：负例是黑盒测试的一部分（5 个 `CosmosAnswerError` 夹具），且 `#42` 铁律写进了 AI 指南的**置顶第一条**。

**兜底话术**：「规范见 `docs/spec/syntax.md` §2.2，设计决策见 `DECISIONS.md` D-013/D-014。」

### Q4 ★★ 「为什么没有 REPL？命令行也不能传参数、不能读文件，这算完整语言吗？」　（概率：高｜杀伤力：中）

**答案要点**：
1. **如实承认**：CLI v1 只支持 `lfz run <file>` 与 `lfz test`，**没有 REPL、没有 `-e`、不能传参、不能读文件/环境变量**。这是**范围裁剪**，不是遗漏。
2. **裁剪理由**：REPL/stdin/`-e` 在 spec 里被定义为**前导 `#42` 的豁免入口**，但 v1 未实现；我们优先把**解释器核心 + 黑盒测试 + 应用**做扎实（评分权重最高的是应用 30 分），而非铺开半成品工具面。
3. **有明文记录**：REPL 与模块、`lfz fmt/doc/init` 等一并列入 **v1.1 backlog**（D-007）；`import` 是**未来保留字**，使用即 `SyntaxError`——语言对未来扩展留了位。
4. **有绕行方案**：应用（sortviz）用**源码顶部常量**代替 CLI 参数，并在 README 给出"改常量→重跑"的**可复现步骤**；`--json` 提供了机器可读出口。
5. **方向**：REPL 与模块在"未来工作"里，实现路径清晰（loader 已有 `load_source` 入口概念）。

**兜底话术**：「backlog 与保留字设计见 `DECISIONS.md` D-007 与 `docs/spec/syntax.md` §2.6。」

### Q5 ★★ 「测试真的覆盖全了吗？有哪些东西你们其实测不到？」　（概率：高｜杀伤力：高）

**答案要点**：
1. **先说覆盖到的**：黑盒 **82 用例全绿**（一键 `cargo run -- test`）；内置函数覆盖 `interface-contract.md` §10.7 全表 **54/54**；错误模型 §8.1 **12 类全覆盖**（11 类黑盒 + `IOError` 由 Rust 单测）；每特性按"正常/边界/错误"建用例。

### Q7 ★★ 「性能打算怎么优化？说个具体方案。」　（概率：高｜杀伤力：中）

**答案要点**（按收益排序，来自 `performance.md` §6）：
1. **先修两处 O(N²)（收益最大）**：
   - `push` 等"返回新容器"内置 → 引入 **copy-on-write / 持久化向量**（未共享时原地 `Vec::push` O(1) 摊销，仅当存在别名时才拷贝，**保持 A1 语义不变**）；同类检查 `pop/removeAt/insert/swap/slice/del`。
   - struct 数据面 → **`IndexMap` 式（HashMap<key→slot> + 顺序数组）**，键 O(1) 定位、新键 O(1) 摊销追加，`keys()` 保持字节序升序（O(n log n) 可接受）。
2. **引入 resolver / 槽位缓存（普遍提速）**：解析期为每个标识符算 `(作用域深度, 槽位号)` 写回 AST；求值期用**数组下标访问**，移除按名字查链；参数绑定用槽位数组、复用调用帧。
3. **中长期：字节码 VM**：把 AST 编译为栈式/寄存器式字节码，在 ①② 收益见顶后再评估；配合少量特化有望缩小乃至反超 CPython。
4. **不动的地方**：进程启动（11.7 ms，已优于 CPython）与原生高阶内建（B4 已 1.20×，改动风险大于收益）。
5. **预期与诚实**：修复 ①② 后**有望**把最大规模比值从"数十倍"拉回个位数；**这是分析性外推，不是已实现数据**，实施后由同一套 harness 复测。

**兜底话术**：「瓶颈定位证据（探针）与优先级建议见 `docs/reports/performance.md` §6 与附录 C。」

## 2. 常规问题（中/低杀伤力）

### Q8 「为什么选这 5 个语言特色？取舍标准是什么？」　（概率：中｜杀伤力：中）

**答案要点**：判据 = **辨识度 × 可行性 × 加分**（D-007）。5 特色：① 管道 `|>` + `_` 占位；② 合一 struct；③ 富字符串插值；④ 结构化错误 + `assert`/`check`；⑤ 确定性语义「无魔法」。**宁可 5 个真正落地拿满分，不要 12 个半成品崩掉解释器和测试两大项**——11 项（生成器/match/模块/类/类型注解等）主动列入 v1.1 backlog。

---

### Q9 「`assert` 和 `check` 有什么区别？为什么要两个？」　（概率：中｜杀伤力：低）

**答案要点**：`assert(cond, msg)` 失败抛 `AssertionError`（**致命**，退出码 2，终止）；`check(cond, msg)` 失败只向 **stderr** 写一行、返回 `false`、**继续运行、不改变退出码**。这对应测试学里的"**硬断言 vs 软检查**"：黑盒 runner 只把 `AssertionError` 判 FAIL，`check` 失败不算（契约 T-R3）。sortviz 用 `check` 做 150 次**非致命属性自测**，用 `assert` 做**致命正确性校验**。

---

### Q10 「struct 为什么把对象和字典合成一个类型？不会混乱吗？」　（概率：中｜杀伤力：中）

**答案要点**：这是核心设计——「**一种结构，两种面孔**」。`struct` 同时具备**对象面孔**（`.字段` / 方法，`self`）和**字典面孔**（`["键"]`），**同源存储**。好处：无需区分"类实例"和"dict"，减少两套概念与转换；`struct Stats` 既能当计数器对象（`self.cmp += 1`），又能当记录打印。**边界规则明确**（A5）：方法**不进入数据面**——`keys/values/entries/has/del` 只作用于数据字段；关键字不能作字段名（用 `r["self"]`）。

---

### Q11 「错误模型为什么取消了编号错误码，只用类名 + 中文消息？」　（概率：中｜杀伤力：中）

**答案要点**：按用户新指令（D-013）**全量改写为 Python 风格错误模型**：命名错误类 + 中文消息 + 位置 + 插入符 + traceback，**取消 `E-xxx` 编号**，并新增 `CosmosAnswerError`。理由：**类名比编号更可读、可 catch、可组合**（12 类对应运行时语义），且 Python 风格对课程受众友好。**加载/解析期错误（`CosmosAnswerError`/`SyntaxError`）无 `Traceback` 头；运行期错误（其余 10 类）有**——这个区分也是刻意设计。

### Q12 「LFZ 的引用语义/闭包是怎么实现的？内存安全吗？」　（概率：中｜杀伤力：高）

**答案要点**：
1. **值模型**：`enum Value` 表示动态值；可变复合类型（array/struct/闭包环境）用 **`Rc<RefCell<...>>`**，故 `array`/`struct` 是**引用类型、传参按引用**（A1）。
2. **引用语义 A1**：容器内置**返回新值、不改原容器**（函数式更新）；唯一原地改的是**赋值语法** `a[i]=v` / `s.k=v`。
3. **闭包（A2）**：**按 cell 捕获**——变量被提升为 cell，多个闭包/循环每轮各自绑定正确捕获，实现"多实例互不干扰"。
4. **环安全（A6）**：`==` 是**深结构相等且环安全**（自引用容器显示 `<cycle>`，不报错、不死循环）；用栈式大栈线程求值，递归超 10000 层转结构化 `RecursionError`（而**不是** Rust 栈溢出崩溃）。

### Q13 「解释器最薄弱的环节是什么？」　（概率：中｜杀伤力：高）★

**答案要点**（坦诚）：
1. **运行时求值的最薄弱**：**无 resolver 的名字查链** + **每次调用新建帧/绑定参数名** + **两处容器 O(N²)**——这三者共同构成性能短板；`evaluator.rs` 是最大的单文件（约 3000 行），复杂度集中。
2. **能力面薄弱**：无 REPL、无模块、无 CLI 参数/文件 IO，语言"外围"尚小。
3. **有 1 个未修缺陷（中等）**：**bug-20260927-01**——方括号取方法值再调用（`p["norm2"]()`）时不绑定 `self`，与 spec `s.k ≡ s["k"]` 的等价性冲突（`.字段()` 路径正常）。**非阻塞、已按流程提交**。
4. **另有 1 个低缺陷**：`lfz test --json` 下 stdout 非单行（`;;` dump 文本仍写 stdout，JSON 恒在最后一行）——`tests/REPORT.md` §3.1 已自认，主命令 `cargo run -- test` 不受影响。
5. **verifier P9 验收口径**：**8 项中 7 项达标**，交付物 8「PPT 已产出、待入库」；**总评 CONCERNS（有条件交付，无阻塞项）**——待闭合项 = 上述 bug-01 + PPT 入库 + README 刷新。
6. **但**：正确性/健壮性侧很强——431 测试全绿、0 告警、P3.11 的 10/10 缺陷闭环、错误模型完整、端到端可用。

### Q14 「开发记录（DEV_RECORD）说 app-dev 是 AI，那这记录是不是 AI 自己编的、可信吗？」　（概率：中｜杀伤力：高）★

**答案要点**：
1. **记录格式要求可核**：DEV_RECORD 逐轮记录"**用了什么提示词 → 得到什么 → 下一轮怎么调整**"，6 轮迭代，并**逐条列出因 SKILL 哪一条做了什么决策**（评分项 4×5 交叉证据）。
2. **可交叉验证**：里面对语言边界的结论（如"`import` → `SyntaxError`"、"`input()` 无 stdin → `IOError`"）都有**最小复现实验**，可现场重跑；应用本身 `cargo run --quiet -- run app/sortviz.lfz` 退出码 0，源码 341 行**逐字节可查**。
3. **有失败记录，未粉饰**：记录了唯一一次会导致失败的缺陷（未定义变量 `stHead`）——**靠指南 §8 自检清单在运行前拦下**；也记录了观感问题（标签超宽）与 O(n) 拷贝等语言限制。**造假者不会写自己的失误。**
4. **诚实口径**：AI 辅助开发是**任务明确要求**的第 5 项（"使用编程 Agent 辅助"）；我们如实呈现 AI 的角色、提示词与实测输出，不夸大为"全自动"。

### Q15 「性能对比公平吗？会不会是 LFZ 手写循环 vs Python 内建这种不平等对照？」　（概率：中｜杀伤力：高）★

**答案要点**：
1. **同算法、同规模、同输出**：两侧同算法、同输入规模（N 经 stdin 传入）；**每轮都断言 `LFZ stdout == Python stdout` 且退出码为 0**，本次 **18/18 全部一致**，不一致即标 `INVALID` 排除。
